    Training Data Execution System

    The complete record of one training run — 19 stages from raw text to audited evidence. What was built, what it ran, the code that ran it, the artifacts it wrote and the records inside them. The model is 1.3M parameters and beside the point; the data system is the work. Every number, every line of code and every record on this page is read from the working tree and the run's own artifacts.

    How to read this

    The page follows the pipeline in execution order, 19 stages. Each gets the same facets, and the weight is on what was built and what it ran rather than on theory — the concept is a snapshot, then the detail. Interactive instruments sit inside the stage they belong to, showing that stage's real output.

    Nothing here was transcribed. The code excerpts are pulled out of the working tree at build time, the records are lifted verbatim from the ledgers, the file sizes are stat'd, and the log lines are sliced from run.log. Change the run and this page changes with it.

    Three views of the same system

    A data system is easiest to misunderstand when you only ever see one view of it. These three answer different questions: what obligations it must satisfy, what code exists, and what actually moves at run time.

    The four things the system has to prove

    “The assignment is complete only when the system can prove what it consumed, why it consumed it, what the model learned from it and how the run can be reconstructed.”

    Every other check verifies one subsystem. This one verifies that the subsystems are joined up — that you can start from a token span the model actually saw and walk, without a gap, to the reason it was chosen, to what the model got back, and to everything needed to rebuild it.

    That is a different property. A run could have a perfect consumption ledger, a perfect OPUS ledger and a perfect learning ledger and still fail here, if an id in one does not resolve in the next. So the test is a link walk over every consumed sample, not a spot check — any dangling reference fails the clause it belongs to.

    Generated, then independently re-verified

    Grading happens in three steps — execute, verify evidence, inspect code — and the third exists to catch simulated behaviour. So the bundle is built to survive it: every check reopens the artifacts and recomputes, and a second program re-derives the same conclusions without trusting the first.

    Requirements

    Every check emitted during the run

    An auditor that can never fail is not evidence of anything. verify_evidence.py re-runs every check, re-verifies every hash chain, and re-derives the headline figures by summing the consumption ledger. Three tests corrupt artifacts — a doctored ledger record, a flipped verdict, a deleted file — and require the verifier to notice each one.

    Reproduce it

    pip install -r requirements.txt python run_demo.py # regenerates submission_artifacts/ from scratch python -m tdes.cli.verify_evidence # independent re-derivation pytest -q # 107 invariant tests python tools/build_report.py # rebuild this page from the artifacts

    Two consecutive full runs produced bit-identical batch ids, token spans, ledger hash chains, all 528 OPUS gradient cosines, and every loss value. Identity here is derived from integers, so the hashes hold regardless of float behaviour; the float reproducibility is a bonus, not a dependency.

    This page is generated by tools/build_report.py, which reads submission_artifacts/ and fails if an artifact it expects is missing. Nothing on it was typed by hand — it would have been inconsistent to hardcode the one document arguing that nothing is hardcoded.
